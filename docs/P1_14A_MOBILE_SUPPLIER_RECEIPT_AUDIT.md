# P1-14A 手机供应商送货单收料：现状审计与离线原型

## 1. 本轮状态

- 任务：Q1-06 / P1-14A。
- 精确开发基线：`229377a90050bb96b6c2f77203ac631ae8b0a911`。
- 原型入口：`docs/prototypes/p1_14a_supplier_receipt_mobile/index.html`。

## 2. 先说清楚：当前系统能做什么

当前 ERP 已有来料收料能力，但还没有“手机拍供应商送货单后识别并生成收料草稿”的正式功能。

当前 `/api/incoming/batch-receive` 的实际行为是：

1. 先检查本批明细的客户范围；
2. 再逐行调用既有正式收料规则；
3. 每行使用独立 savepoint；
4. 一行失败时，其他合格行仍可能成功；
5. 返回 `succeeded`、`failed` 和逐行结果；
6. 审计结果明确区分 `success`、`partial`、`failed`。

因此，当前接口是“逐行处理、允许部分成功”，不是“整张送货单全部成功或全部回滚”的原子接口。本轮原型只演示核对步骤，按钮文字使用“查看提交前汇总（演示）”和“完成演示（不入库）”，不得让员工误以为已经调用正式收料。

## 3. 现有能力审计

### 3.1 可直接复用的能力

| 能力 | 当前证据 | P1-14 后续可复用方式 |
|---|---|---|
| 供应商主档 | `supplier_master_records`、`supplier_master_aliases`，支持启停和别名 | 用启用供应商及别名辅助识别，不新建第二套供应商表 |
| 来料权限 | `incoming.view`、`incoming.execute` | 手机页继续使用独立员工账号和服务端权限校验 |
| 正式收料规则 | `app/api/incoming.py`、既有收料服务 | 后续正式提交必须复用短收、超收、幂等、撤销和客户范围门禁 |
| 三类实物来源 | `requisition_item_bom_sources` 及 Q1-01 回归 | 匹配时必须落到具体实物来源，不能只靠尺寸或数量猜 |
| 全业务审计 | `operation_logs`、`append_audit_event` 及 Q1-02 回归 | 上传、查看、改稿、匹配、提交失败和正式收料分别记录 |
| 待报料等候门禁 | `requisition_holds` 及 Q1-04 回归 | 活动等候明细不能被手机识别流程绕过并变成正式收料 |
| 私有上传校验底座 | `app/services/secure_uploads.py` | 后续可复用签名、MIME、大小、SHA-256、私有路径和临时令牌 |

### 3.2 当前缺口

当前没有以下正式能力：

- 供应商送货单照片草稿；
- 多页照片、缩略图和拍照重试；
- OCR 原文、识别版本、识别置信度和人工修正；
- 供应商单号、单据日期、行号和图片哈希查重；
- OCR 行与报料实物来源的候选匹配；
- 仅凭 `incoming.view` 且受客户范围保护的来料附件查看入口；
- “近期来料可生产”专用只读聚合页；
- 整张送货单原子确认服务。

不能把客户订单 PDF 识别接口改名后复用；供应商送货单的字段、候选范围和数量事实不同。

## 4. P1-14A 的最短演示流程

### 4.1 正常情况

1. 员工进入手机收料页。
2. 点击“载入匿名照片演示”。
3. 点击“开始识别演示”。
4. 页面只展开需要处理的异常；正常明细保持紧凑。
5. 异常处理完后，点击“查看提交前汇总（演示）”。
6. 点击“完成演示（不入库）”。

这六步全部发生在浏览器内存中，刷新页面后恢复初始演示数据。

### 4.2 异常情况

- 短送：选择“剩余继续等”或“按本次数量结束”。
- 超送：选择“全部用于本单”或“多余放客户专用纸板备料（演示）”。
- 未送：选择“本次未送，继续留待收”。
- 多候选：人工选一条候选，或交给办公室处理。
- 疑似重复、照片模糊：只显示阻断说明，不产生任何收料事实。

## 5. 数量和匹配规则

### 5.1 三个数量必须分开

| 数量 | 来源 | 是否可由 OCR 覆盖 | 说明 |
|---|---|---:|---|
| ERP 待收数量 | 报料/实物来源事实 | 否 | 正式业务基准 |
| 供应商单据数量 | 图片识别后人工核对 | 是 | 供应商写在单据上的数量 |
| 现场实收数量 | 员工现场核对 | 是 | 后续正式提交时才可能形成收料事实 |

“未送”不能通过写入 0 数量来关闭待收明细。

### 5.2 候选匹配顺序

| 顺序 | 条件 | 处理 |
|---:|---|---|
| 1 | 启用供应商 + 报料单号 + 实物来源明细号唯一 | 可自动推荐，仍展示关键事实 |
| 2 | 启用供应商 + 客户 + 存货编码 + 活动实物来源唯一 | 可自动推荐 |
| 3 | 同客户、同存货编码有多条活动来源 | 展示候选，必须人工选择 |
| 4 | 只有尺寸、材质或数量相似 | 不自动匹配，交给办公室 |
| 5 | 找不到活动来源、供应商停用、客户越权、Q1-04 仍在等候 | 阻断，不临时创造正式明细 |
| 6 | 同供应商单号或图片哈希疑似已处理 | 阻断重复提交，提供原记录只读入口 |

匹配候选只展示供应商、报料单、客户、存货编码、规格、材质和剩余待收数量；不展示成本、价格或技术评分。

## 6. 异常文案矩阵

| 场景 | 员工看到的文字 | 本轮原型结果 | 后续正式规则 |
|---|---|---|---|
| 正常 | `数量一致，无需处理` | 保持折叠 | 仍需服务端校验 |
| 短送 | `少到 20 张` | 记录演示选择 | 复用既有短收门禁 |
| 超送 | `多到 20 张` | 记录演示选择 | 复用超收及库位门禁 |
| 未送 | `现场没有这款` | 保持待处理演示 | 不创建 0 数量收料 |
| 多候选 | `找到 2 条，请选对应报料` | 记录演示候选 | 未选时禁止正式提交 |
| 疑似重复 | `可能已经收过，先查看原记录` | 阻断演示 | 服务端幂等和查重 |
| 图片模糊 | `照片看不清，请重拍` | 阻断演示 | 不进入匹配 |
| 数据变化 | `数据已变化，请重新核对` | 仅展示说明 | 服务端版本门禁 |

## 8. 附件边界

后续真正接照片时应满足：

- 原图和缩略图放在私有 UUID 路径；
- 校验扩展名、MIME、真实文件签名、大小、页数和 SHA-256；
- 下载使用登录、`incoming.view`、客户范围和短时令牌；
- 响应使用私有、禁止缓存策略；
- 不把原图、OCR 全文、账号、令牌或敏感载荷放进 URL、日志或 `localStorage`；
- 原图保留时长、单文件大小和最大页数必须在 P1-14B 使用真实匿名样本确认。

本轮原型没有 `<input type="file">`，也没有相机权限、上传或照片持久化。

## 10. “近期来料”只读建议

数据入口必须是正式 `IncomingReceiptItem`，不能用 OCR 草稿或照片代替收料事实。

建议显示：

- 收料日期、收料人、供应商和供应商送货单号；
- 客户、存货编码、产品、规格、材质、楞型；
- 本次实收、累计已收、仍待收；
- `材料已齐` 或 `材料未齐`；
- 模具名称和位置；
- 送货单缩略图及订单/产品图纸只读入口。

不得出现确认生产、移动库存、自动扣料或完工按钮。

- 不从 OCR 草稿生成“可生产”事实；
- 不提供写业务数据的按钮。
