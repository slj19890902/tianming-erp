## 3. 指标合同

### 3.1 客户总体

只纳入 `customers.status='active' AND customers.is_active=1` 的当前活跃客户主档。未来服务端查询必须先应用登录账号的客户范围，再聚合和分页；不允许先对全体客户计算后再隐藏。

### 3.2 有效订单

有效订单必须同时满足：

- 来自正式表 `sales_orders`；
- `order_number` 非空；
- `order_date` 不晚于统计日；
- 状态不属于 `dead/cancelled/canceled/void/voided/draft/test`。

`completed/closed/archived` 是已经发生的正式历史订单，仍属于客户历史活跃事实，不能因为不在日常业务队列就删除。

当前表结构没有独立 `is_test` 标记。审计程序会排除明确的 `test` 状态，但禁止按客户名、单号前缀或备注猜测测试订单。进入 P1-61B 前必须确认正式 `sales_orders` 不混入使用正常状态保存的测试单；否则另立数据治理任务，不能为个别客户写名称特例。

### 3.3 主单去重

先按 `sales_orders.id` 聚合明细，再进入客户聚合：

- 一张主单有多条 `sales_order_items` 时，近 365 天订单数只加 1；
- 同一天有多张不同主单时，主单数按实际张数增加；
- 同一天无论多少主单，近 90 天下单天数只加 1。

### 3.4 时间窗口

以业务统计日 `as_of` 为闭区间终点：

- `R`：统计日减最近一张有效订单的 `order_date`；
- 近 90 天下单天数：`as_of-89` 到 `as_of` 的不同 `order_date` 数；
- 近 365 天主单数和金额：`as_of-364` 到 `as_of`；
- 最近有效订单超过 365 天，固定归入最低活跃候选；
- 从未有有效订单的客户不冒充“新客户”，单列为“无有效历史”。

### 3.5 新客户

满足任一条件即标记为新客户候选：

- 全部有效主单不足 3 张；
- 第一张到最近一张有效订单的历史跨度不足 30 天。

新客户标签优先于普通分位分档，避免刚开户客户因样本太少被误判为高热或低热。

### 3.6 冻结金额与完整率

金额只使用订单保存时已经冻结在 `sales_order_items.unit_price/subtotal` 的历史事实，不查询当前产品价格或客户当前报价。

- 每张主单先汇总自己的明细小计；
- 任一明细 `unit_price` 缺失或不大于 0，整张主单金额标记“不完整”；
- 近 365 天任一主单金额不完整时，客户的“完整冻结金额”返回 `null`，不能返回 0；
- 同时保留已知冻结金额和金额完整率，用于诊断缺口；
- 无金额权限时，客户级金额和金额分位数全部返回 `null`，不能先计算精确金额再在前端隐藏。

## 4. 一条 SQL 批量聚合

审计程序的核心聚合每次只执行 1 条 SQL：

1. `valid_master_orders` CTE 把订单明细压成一张主单一行；
2. `customer_rollup` CTE 按客户同时计算 R/F/M 和金额完整率；
3. Python 只负责匿名化、分位数摘要和报告渲染，不逐客户查询数据库。

P1-61B 必须继续保持“客户范围条件进入 SQL、服务端分页、按需展开”，禁止前端拉全量订单计算热度，也禁止后端逐客户 N+1。

## 5. 旧真实副本预演结果（不用于最终阈值）

旧 `cr74v8x9z63` 真实数据隔离副本的匿名摘要：

- 活跃客户主档：92；
- 新客户候选：10；
- 沉睡或无有效订单：81；
- 能进入近期成熟客户分位计算的客户：仅 1；
- 近 365 天订单金额完整率：1.0；
- 核心聚合：每次 1 条 SQL；
- 5 次响应：median 0.443 ms，p95 0.967 ms；
- 查询计划：扫描订单主表，通过 `ix_sales_order_items_order_id` 关联明细，并为客户聚合创建自动覆盖索引及临时去重树；
- 现有索引中没有 `(customer_id, order_date)` 复合索引。

这份旧副本在统计日只有 1 个近期成熟客户，任何 P20/P40/P60/P80 都会退化成同一个值，不能作为热1～热5阈值。它只能证明当前数据规模下单 SQL聚合没有 N+1，并暴露未来服务端分页查询需要继续观察的索引方向。

## 6. 阈值建议边界

本阶段可固定的只有任务书已经确认的业务规则：

- `recency_days > 365`：最低档候选；
- 有效主单不足 3 张，或历史不足 30 天：新客户；
- 金额只做低权重和同档次序，金额缺失不当 0。

当前正式隔离副本完成复跑后，可把成熟客户的 R、近 90 天下单天数、近 365 天主单数和完整冻结金额的 P20/P40/P60/P80 作为原型候选切点。它们仍不是最终阈值；最终权重、五档阈值和色值必须由 P1-61C 人工原型验收确认，并使用有版本、可审计的配置，而不是散落在代码里的常量。

## 7. 索引建议

P1-61A 不新增索引、不迁移数据库。P1-61B 开发前应在当前正式隔离副本上先实现带客户范围、排序和分页的真实查询，再用 `EXPLAIN QUERY PLAN` 与响应时间判断是否需要 `(customer_id, order_date)` 或面向有效状态的组合索引。

仅凭旧全量诊断 SQL 的 `SCAN sales_orders` 不足以授权迁移，因为：

- 当前数据量很小；
- 未来查询必须先带客户范围与分页；
- 复合索引会增加订单写入成本；
- 当前任务默认无迁移。

```powershell
$env:P1_61A_ANONYMIZATION_KEY='<仅本次报告使用的随机密钥>'
python scripts/audit/p1_61a_customer_heat_distribution.py `
  --database '<隔离副本绝对路径>' `
  --json-output '<匿名JSON报告绝对路径>' `
  --markdown-output '<匿名Markdown报告绝对路径>' `
  --source-label 'formal-isolated-copy-YYYYMMDD' `
  --as-of 'YYYY-MM-DD' `
  --expected-revision 'mm21v8x9z10' `
  --expected-sha256 '<复制后SHA-256>' `
  --iterations 5 `
  --include-amounts `
  --amount-authorized
Remove-Item Env:P1_61A_ANONYMIZATION_KEY
```

命令没有 apply 模式。revision、SHA、完整性、外键、金额权限或只读门槛任一不满足时，程序直接失败且不生成成功报告。
