# 订单主系统单号与明细子编号设计稿

更新时间：2026-06-21 00:53:04

1. 是否确认目录：是，`D:\纸箱厂erp软件搭建`
2. 是否执行历史迁移：否
3. 是否修改历史订单：否
4. 是否修改 `legacy_*`：否

6. 未经单独授权，不直接修改主库结构，不直接创建正式测试订单。

## 二、核心理解

本方案按以下口径执行，不再沿用旧误解：

1. 一张新建订单生成一个主系统单号。
2. 同一张订单下的每条明细生成一个明细系统单号。
3. 客户单号是客户提供的外部单号，不是系统编号，也不是唯一键。
4. 订单管理默认按 `customer_id + customer_po` 分组，而不是按系统单号或仅按客户单号分组。

## 三、编号规则

### 1. 主系统单号

格式：

```text
TMYYYYMMDDNNN
```

示例：

```text
TM20260620001
TM20260620002
```

规则：

1. 每新建一张订单生成一个新的主系统单号。
2. 主系统单号全库唯一。
3. 主系统单号按天递增，序号范围至少 `001-999`。
4. 删除或作废主订单后，主系统单号不复用。
5. 前端可以预览主系统单号，但以后端最终保存结果为准。

### 2. 明细系统单号

格式：

```text
主系统单号-明细序号
```

示例：

```text
TM20260620001-001
TM20260620001-002
TM20260620001-003
```

规则：

1. 每条订单明细都有唯一明细系统单号。
2. 明细系统单号全库唯一。
3. 明细序号在同一主系统单号下递增。
4. 删除或作废明细后，子编号不复用。
5. 例如已有 `-001/-002/-003`，删除 `-002` 后再新增，必须生成 `-004`。
6. 前端只做预览，后端保存时生成最终明细系统单号。

## 四、订单管理正式分组规则

默认分组规则：

```text
group_key = customer_id + customer_po
```

必须满足：

1. 只有“同一客户 + 同一客户单号”才归为一组。
2. 不同客户即使 `customer_po` 相同，也绝不合并。
3. `customer_po` 为空时，不参与合并，按单独主系统单号各自显示。
4. 客户单号不是唯一键，不能单独用 `customer_po` 分组。
5. 搜索命中后，结果仍按 `customer_id + customer_po` 分组。

## 五、订单管理默认显示规则

默认视图要求：

1. 第一列显示：客户单号。
2. 第二列显示：编辑按钮。
3. 系统单号默认隐藏。
4. 默认按 `customer_id + customer_po` 分组。
5. 主行建议显示：
   - 客户单号
   - 编辑
   - 客户名称
   - 订单日期范围
   - 子单数量
   - 总数量
   - 总金额
   - 状态
   - 展开
6. 展开后显示：
   - 明细系统单号
   - 主系统单号
   - 产品名称
   - 存货编码
   - 规格
   - 材质
   - 数量
   - 单价
   - 金额
   - 状态

展开示例：

```text
TM20260620001-001
TM20260620001-002
TM20260620001-003
```

## 六、搜索规则

订单管理搜索必须支持：

1. 客户名称
2. 客户单号
3. 主系统单号
4. 明细系统单号
5. 日期搜索或筛选
6. 产品编码
7. 产品名称

搜索结果要求：

1. 结果仍按 `customer_id + customer_po` 分组。
2. `customer_po` 为空的命中结果仍单独显示，不强行合并。
3. 搜索不能把不同客户的相同客户单号混在一起。
4. 系统单号默认隐藏，但可在展开详情或管理员高级信息中查看。

## 七、字段与结构评估结论

基于需求口径，预计至少需要评估以下字段：

### 1. 可能需要新增的字段

建议评估是否新增：

```text
sales_order_items.item_order_number
sales_order_items.item_sequence
```

说明：

1. `item_order_number`：保存明细系统单号，建议全库唯一。
2. `item_sequence`：保存同一主系统单号下的明细递增序号。

### 2. 可能需要新增的序列表

建议评估是否新增：

```text
order_daily_sequences
```

建议职责：

1. 记录每日主系统单号最大序号。
2. 保证主系统单号删除/作废后不复用。
3. 如现有结构不能可靠保证明细子编号不复用，可补充同类明细序号策略。

## 八、索引建议

实现前必须先检查现有索引是否已存在，避免重复创建。

建议评估以下索引：

```text
sales_orders.customer_id
sales_orders.customer_po
sales_orders.order_date
sales_orders.order_number
sales_order_items.item_order_number
sales_order_items.snapshot_product_code
sales_order_items.snapshot_product_name
```

约束：

1. 如果索引已存在，不重复创建。
2. 如需新增索引，先在副本验证性能与完整性。
3. 未经单独授权，不直接改主库结构。

## 九、后续实现测试标准

后续实现必须覆盖：

1. 同一客户 + 同一客户单号会合并。
2. 不同客户 + 相同客户单号不会合并。
3. 空客户单号不会强制合并。
4. 搜索客户单号后仍按 `customer_id + customer_po` 分组。
5. 搜索主系统单号能定位订单。
6. 搜索明细系统单号能定位对应明细。
7. 订单管理第一列为客户单号。
8. 编辑按钮在第二列。
9. 系统单号默认隐藏。
10. 展开后显示主系统单号和明细系统单号。
11. 主系统单号按天递增。
12. 明细系统单号按主系统单号下递增。
13. 删除或作废后主系统单号不复用。
14. 删除或作废后明细系统单号不复用。
