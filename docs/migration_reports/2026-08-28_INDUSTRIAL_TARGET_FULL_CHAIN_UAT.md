## 3. 本轮实现

### 3.1 响应速度与查询规模

- 应用启动时缓存 settings，并让认证、依赖、安全和主路由复用，移除每请求重复 UAT 路径校验造成的约 235ms 固定开销。
- 仓库读取移除重复 eager load；Windows UAT 所有权清理改为有界等待。
- 报料 pending、待发货 pending/search、送货列表/详情和首页待送货统计改为批量上下文或页内订单号 registry，避免全表订单扫描和 N+1。
- 24 张送货单列表、报料列表、待发货搜索及首页待送货卡均建立固定查询上限回归。

### 3.2 对账、开票与收款

- 保留 `Statement.version` 作为来源快照版本，新增独立 `ledger_version` 作为开票/收款账务 CAS 版本；避免人工开票、收款和开票任务互相误判来源已失效。
- 人工开票、人工收款和开票任务成功登记使用数据库条件更新 CAS；金额上限、状态、来源版本和 ledger 版本同一事务校验。
- 新增 `finance_manual_mutations` 幂等事实表；同操作者同载荷重试返回原成功结果，不同操作者、不同载荷或系统保留命名空间返回 409。
- 开票任务 `issued`、`failed`、`voided` 都受状态与版本 CAS 保护；旧会话不能用失败/作废覆盖已成功记账任务。
- 请求哈希包含 `failure_reason`，避免忽略字段后的异载荷重放。
- 审计失败、唯一键冲突或任一后续异常会回滚 statement ledger、任务状态、发票/收款记录和幂等事实。
- 订单回退在存在非草稿财务事实时 fail-closed；外键并发冲突统一映射 409。
- 前端对账/开票的不确定提交以操作者作用域保存冻结载荷、幂等键和双版本，可恢复、可重试且防旧响应覆盖新会话。

### 3.3 送货、库存、报料与地图一致性

- 混合“成品库存 + 半成品库存”订单统一使用累计成品来源覆盖口径；首批发货后的 pending、搜索、详情、列表、再次发货和撤销来源数量一致。
- 同一订单多批送货不再把半成品已发数量重复算成成品覆盖；成品 BOM component reservation 不参与主件发货来源。
- 成品/半成品消耗与撤销保持对称，实际库存、计划拣货和 UI 展示共用同一 helper。
- 已占用当前库位/货架栈板在区域容量已满时仍允许给原栈板加货；新栈板、伪造 ID 或其他库位栈板继续 409。
- 报料列表保留产品批量加载，按用途聚合准确数量；已提交报料页面给出明确状态提示。
- 当前地图迁移空库判定同时检查订单、库存批次和栈板事实；有业务事实但缺地图快照/RAW-001 时继续 fail-closed。
- 地图 API 使用 canonical `position_status` / `map_issue`；列表与详情一致，1F/3F 孪生布局可读。旧版 `factory-map` 按既有契约只配置 1F，3F 返回明确 404，不作为 3F 孪生地图入口。

### 3.4 页面交互和 UI 稳定性

- 来料、订单、报料、送货、财务和开票任务的异步加载增加 latest-request、会话代次和操作者防串线保护。
- 订单保存先进入 saving 门禁，再执行异步模具预览，避免双击重复创建。
- 库存补货作废入口恢复 document id、权限、确认和不确定提交保护。
- 财务恢复草稿包含操作者、版本、金额、日期、幂等键和目标对象，跨账号不会恢复。
- 修正来料页 Tailwind 本地资源精确 SHA；页面仍使用本地静态资源，不引入运行时 CDN。
- 更新陈旧 UI/迁移测试断言以匹配已发布正式合同，未削弱生产权限、状态、数量、事务、幂等或 fail-closed 门禁。
