# 第三阶段详细实施方案：多人操作与异常恢复

状态：planned。日期：2026-09-21。编制本方案，不执行功能开发或发布。用户要求现场验收在日常工作完成，下一阶段由 Terra 持续推进技术任务。

## 一、为什么做这一阶段

第二阶段 R00—R06 已收尾，真实 IME/受限账号两项由管理员确认。它没有证明所有设备或所有场景分支通过。旧 T16 仅20/24行及1/3/5并发读取的同机探索，明确排除了普通保存、写热点和正式峰值；T19 因无证据继续保持SQLite/DELETE。R00索引部分条目仍仅历史局部证据。因此下一阶段补真实写入口的竞争/重试和规模证据，按结果修复，不以旧EXE形式为理由重写系统。

依据：上一阶段 `R00_证据索引.md`、旧 `tasks/T16.md`、`tasks/T19.md` 以及总需求的幂等、数量守恒、权限和事务要求。这里描述待验证分支，不宣称已发现新缺陷。

## 二、成果与非目标

交付：一套可重复隔离数据夹具；并发/丢响应/权限的真实应用接口证据；规模分档报告；仅针对失败的最小修复；准确的版本/包/备份/回退交接。

保留网页前端、统一服务端、集中SQLite、桌面助手与现有签名链。不做原生EXE业务重写、数据库换引擎、WAL开关、辅料台账、计件工资、多地址、总账税务、微服务或新的监控平台。未知制度独立记入条件清单，不阻塞当前技术主线。

现场反馈随时插入缺陷记录；没有反馈不创建假问题。不得为完成本阶段制造正式订单或更改库存、付款等业务事实。

## 三、执行顺序与预算纪律

P00 → P01 → P02 → P03 → P04 → P05 → P06。串行单代理，每卡完成证据后进入下一卡。每卡最多先尝试一次完整定向集合；失败精确定位，不反复全文读文档、不反复运行全仓。多次失败归因到环境、基线或产品，再决定后续最小动作，不设置省 token 的虚假完成门槛。

每卡必记：起始源码、隔离目录/解释器、场景ID、实际写入口、期望与实测、命令、起止时间、退出码、报告摘要、变更文件、发布决定、剩余分支。报告用合成ID，隐藏凭据和客户事实。

优先复用 `scripts/qa/run_pytest_with_artifacts.py`。确认环境隔离后运行模板：

```powershell
& $python scripts/qa/run_pytest_with_artifacts.py --report-dir $newReportDir -- <本卡确切测试路径> -q --tb=short
```

$python 必须是 P00 核验过的独立解释器；$newReportDir 必须不存在且在本阶段证据根内。禁止把模板尖括号原样运行。session_id 用 write_stdin 等待同一进程；cell ID 用 wait。保存结束退出码，不从部分输出推定通过。

## 五、性能判定与安全上限

合成数据规模默认100、1000、5000订单，每单1—3明细，包含可解释的采购/库存/已履行状态分布；夹具直接构造历史状态须明确是性能夹具，不冒充通过业务API的主链证据。无法符合模型约束则降档并记录限制，不写“已覆盖大规模”。不假称这些数量代表工厂实际总量。

在固定每页20或50行、固定过滤条件下，串行及1/3/5并发读取采样，预热5次后每档至少30个完整请求。记录实际样本数、p50/p95/max、失败/锁等待/SQL条数、数据行数、CPU/存储/版本和冷热缓存范围。p95是探索指标，不是正式峰值保证。

列表p95≤1秒沿用旧T16参考目标，仅针对同机隔离API。保存延时不编造SLA；先报告锁等待与正确性，错误率不通过扩大超时掩盖。写竞争先固定2请求，最多5并发，不做无上限压力。磁盘剩余小于10GiB、数据库增长超预算或连续服务异常时停止负载、保存证据，不清理他人文件/进程。正式服务绝不注入负载。

N+1判定要求固定分页下查询数随返回行数线性增长的证据；全量读的工作量增长需单独解释。优化前后比较同一夹具与投影，不能靠只改绝对查询预算通过。

## 六、发布和外部验收

无应用运行变化：提交测试/报告即可，不生成版本。应用变化：每个可独立交付闭环按现有授权和发布门禁交付；多个相互依赖修复可在P06统一发布，不能留下高风险代码已合入但无验证。远端变化先核对等价/祖先关系再处理。

必要迁移完整读 MIGRATION_PLAN/RUNBOOK/CHECKLIST，新备份、唯一head、隔离升降升及非空事实拒降；不能因性能理由顺手改引擎。既有签名身份不可用时不替换身份。

正式页不自动点击。老板已取消本任务自动视觉检查：有用户可见交互变化才列1—3条日常检查，无可见变化仅报告接口/测试证据，不要求重复登录验收。记录待人工不停止其余独立工作。已有人工“通过”只覆盖明确那次范围。

## 七、最终验收门槛

1. 所有新增场景有来源和精确断言，不用大测试数代替覆盖关系。
2. 并发确有独立连接/事务和重叠窗口；串行调用不得标并发。SQLite内存共连接不作为锁竞争证据。
3. 丢响应发生在应用提交后/客户端收到响应前，不直接插入结果表冒充成功保存；失败注入不mock掉被测业务。
4. 受限身份由真实权限模型产生，不在前端改布尔值冒充权限。
5. 规模夹具与主链功能测试分开标注；性能未达标不因无限提高预算写通过。
6. 未解决关键正确性/权限问题必须阻止相关正式交付；记录独立恢复条件。
7. 两套旧清单若未修改则不重写；本阶段清单覆盖全部新文档/代码/报告摘要，区分历史快照与当前文件。源码、文档、包及运行基线分别填写。
8. 有应用变化才有新版本；有现场人工确认才标人工通过。没有新缺陷也可凭证据 verified_existing 收尾。
