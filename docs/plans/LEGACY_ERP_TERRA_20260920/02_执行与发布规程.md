# Terra 单卡执行与交付规程

## A. 进入一张卡

1. 按 CODEX_START 的顺序读取入口、NAS、当前卡、一个模块及总需求相关章节。首次读01，后续只读03和当前卡；共享规程只读本次必要小节。
2. 核查 git status --short、当前分支、HEAD、远端正式头。根工作区有他人改动则记录路径和哈希，从已核验远端正式分支创建独立 codex/ 分支/worktree。不能清理他人文件或直接切换脏根目录。
3. 确认当前任务是否已被较新版本等价交付；查对应任务编号、commit和测试，禁止合入旧整分支。
4. 在卡的“执行记录”填写实际文件allowlist、函数/API/模型、已确认规则、依赖、失败用例及回退。卡中给的是搜索起点，未确认的路径不能当成精确实现。
5. 不先全文读取 static/index.html、app/api/orders.py 等大文件。先 rg -n 查函数、字段或错误，再读取命中前后必要范围；没有命中再缩小替代关键词。
6. 采用单代理。不要为省时间并发写文件、并发迁移或并发发布。

可用只读命令模板，逐条按依赖执行：
```powershell
git status --short
git branch --show-current
git rev-parse HEAD
git ls-remote origin refs/heads/factory-current-baseline
rg -n '精确任务关键词' app static tests docs/tasks docs/release_reports
```
网络失败只能记录未核验；不得把本地origin缓存当已读取远端事实。

## B. 隔离及测试

1. 先定位仓库配置解析、测试fixture和迁移env，明确哪一个环境变量最终控制DB。仅设置SQLAlchemy URL不保证覆盖项目配置。
2. 正式库仅用显式只读连接检查。需要副本时采用项目支持的一致性在线备份方式，不直接复制正在写入的SQLite主文件。
3. 给本卡建立独立目录，记录副本来源、时点、数据库绝对路径、代码SHA、迁移head。打开应用前确认实际生效路径不等于正式库、共享业务目录、其他仍使用中的UAT。
4. 测试fixture及子进程都必须继承隔离路径。邮件、打印、OCR云调用、共享目录写入和定时任务根据本卡需要封锁或替身处理。
5. 已证明隔离的本地UAT可按老板既有约定使用测试账号密码123456；必须先确认账号与隔离数据库，不重置正式账号。
6. 先执行能证明缺口的最小测试。写入功能需测事务、幂等和权限；低风险文案布局不机械造大量镜像测试。
7. 使用 .venv 实际可用解释器；执行前核对fixture，不直接在未知配置下跑pytest或导入app入口。
8. 测试命令模板：<解释器> -m pytest <当前卡精确测试文件> -q；Node测试按该卡给定文件运行。测试输出完整落本地证据目录，只返回摘要与失败节点。
9. 新增模型/字段才讨论迁移。完整读取 docs/MIGRATION_PLAN.md、MIGRATION_RUNBOOK.md、MIGRATION_CHECKLIST.md；唯一head、隔离升降升、非空降级阻止、完整性和FK均需证据。
10. 无代码变化时可用已有有效测试与针对性验证结束；版本和环境变化使旧证据失效时才重跑。

所有敏感字段、客户资料、PDF原文不放通用回执、Git或聊天输出。测试日志只留脱敏身份与必要数字。

## C. 修改方法

1. 从失败用例定位真正原因；保留权限、客户范围、数量、状态、版本、幂等、事务、审计。
2. 模型/事务先行，再接API和UI。局部服务可小步提取，不重写整个订单、财务或前端工程。
3. 前端状态恢复按当前账号、页面、对象、必要版本区分；不持久化令牌、完整业务载荷或假成功状态。
4. 库存量只能来自服务端事实投影。失败返回明确可恢复信息，不用“放宽校验”“异常吞掉”换成功。
5. 同键异载荷拒绝，同键相同载荷恢复同结果；提交结果不确定时先查原结果。
6. 任何新索引/约束先扫隔离数据冲突；发现历史重复不擅删，单独提出数据治理任务。
7. 范围超出allowlist时先在卡中写出必要原因。普通实现扩展可直接继续；业务规则变化或正式数据治理必须另取明确范围。

## D. 定向回归与证据

每卡证据包含：代码SHA；环境/副本身份；场景ID；请求/操作身份；前后事实；HTTP及业务错误；回读结果；测试命令及退出码；未覆盖项。
按风险选择：正常、空值、边界数量、普通角色、跨客户、同键重放、同键异载荷、旧版本、并发竞争、第二行故障、审计失败、历史打印。
结束检查 git diff --check；核对文件allowlist、资源引用和构建产物。不要把长日志提交仓库。
相同失败只在新证据或代码变化后重跑；既有失败可在干净基线复现归因，不能直接标“非本次”。
正式页面禁止自动点击。隔离Chrome验证可执行，禁IAB和批量清理浏览器。
实体打印、手机、扫码枪结果必须由实际验证提供，自动化不得代填。

## E. 提交与发布

本方案编制不执行以下动作。Terra在收到执行指令、确认任务授权和机器角色后使用。
普通已授权修复/功能按既有老板指令继续交付，不反复问提交发布权限；家庭端只做候选，由工厂受控执行正式步骤。
1. 提交前刷新远端正式基线，比较是否有新提交；必要时重放候选并重跑受影响测试，保留其他已发布能力。
2. 显式 git add 当前卡文件。不能 git add . 带入无关文档、数据、日志或密钥。
3. 测试/文档无运行改动不制造版本、不重启服务；功能改动分配未使用版本，更新版本验收元数据。
4. 复用 desktop_assistant/build.py、publish.py、manager.py 等现行签名包/托管更新流程；先读当前CLI帮助及最新成功发布回执，不复制过期部署命令。
5. 比对正式运行包、Git代码、更新源、数据库路径/head，核对独立迁移链和回滚兼容性。
6. 按正式流程制作时点完整备份，并回读验证可恢复、附件及摘要；文件存在不等于备份通过。
7. 有迁移时在副本演练；保护原表事实，新字段缺值按明确历史策略处理；不以数据库覆盖代替迁移。
8. 发布包签名/资产摘要/引用闭合通过；集成、发布更新源、运行端切换的先后顺序遵循现行受控发布流程，记录每一步成功与失败，不凭文档制造已上线状态。
9. 只读检查 /api/health、相关受控API和静态资源。核对实际运行包、版本、数据库revision、完整性/FK、回滚点。
10. 有模板/快照等新业务事实后，不能直接降级删表/删列；恢复旧备份会丢失备份后的业务，应先评估并获明确数据恢复范围。默认优先兼容代码回退或向前修复。
11. NAS独立回执记录代码commit、文档commit、包SHA、备份、迁移、测试、健康、业务数据写入边界、待验收。文档commit不冒充已部署代码commit。
12. 实际前端变化才记录1～3条待验收步骤并继续下一卡；不向老板提问或等待回复。状态保留“待Astra/管理员最终验收”，不得代填通过。
13. 当前任务不改长期规则和正式基线时，不随手扩写全局HANDOFF。

## F. 控制上下文与token

- 不重新审计已关闭项；每卡只带进度行、任务卡、模块契约、相关函数片段。
- 每批独立检索可一次运行，限制返回行数；全部日志在文件，聊天只报根因和下一动作。
- 默认不派子代理、不重复交叉审查、不自动请求更大模型。
- 业务高风险依靠最小失败测试、事务/来源证据和明确规则，不能靠“模型更强”代替。
- 目标运行期间只给简短非提问式进度；不在卡间输出需要用户回复的中间结论。
- 同一类问题连续两次无新证据，停止盲重试：留下最小复现、已排除原因、准确阻塞，再推进独立卡。
- 换模型不会保证已用历史上下文变短；使用本文件的短续接提示、当前卡与进度表控制新任务输入。
- 不承诺具体计费或token节省比例，不把不可获取用量估算成真实数值。

## G. 结束一张卡

更新03进度、卡内执行记录和一份NAS回执。记录下一卡与阻塞。状态只能是：
planned / ready / in_progress / verified_existing / candidate / released_pending_astra_acceptance / accepted / blocked / deferred_with_evidence / deferred_safety_boundary。
每卡关闭后立即推进下一张依赖满足的卡。blocked只能表示当前仍有安全且可行的工作尚未解决，不能用来提前结束整体目标；外部设备、未启用业务或超出授权的有损动作使用两类deferred并写证据。
