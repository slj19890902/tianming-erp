## 3. 换密安全包

### 3.1 写入前门禁

脚本必须同时满足以下条件才会进入交互输入和写入：

1. `--managed-root` 的受管状态、当前发布清单和共享数据库路径互相一致；
2. 目标数据库恰好包含四个指定账号，角色、启用状态、字段和 bcrypt 哈希格式兼容；
3. API 地址必须精确匹配受管配置允许的 HTTPS 入口。普通局域网和公网明文 HTTP 一律拒绝；公网入口不可用时，使用临时本地 CA 校验的回环 TLS 代理，禁用环境代理和重定向，并把 socket 和上游都限制在回环地址；
4. `/api/health` 返回 JSON 且服务正常；HTML 页面响应不能代替 API 判定；
5. 通过 SQLite backup API 建立一致性备份，备份 `integrity_check=ok`，并恢复到另一个临时文件再次校验可读；
6. 四个新口令均由操作人在无回显终端输入并二次确认，符合当前策略且互不相同；四个旧口令仅保留在进程内用于失效验证。

### 3.2 一致性与状态

- 四个密码哈希、`must_change_password`、`auth_version` 和必要审计在同一 SQLite 事务提交。
- 写入前用 `auth_version` 做乐观并发检查；任何账号发生并发变化则整笔回滚。
- 结果 JSON 只保存脱敏状态、版本、路径、备份校验和与 HTTP 判定，不保存新旧口令、Cookie 或令牌。
- 状态明确区分 `not_written`、`committed_pending_verification`、`verified`、`verification_failed_after_commit` 和 `failed_before_commit`。
- 写入后网络验证失败时不自动再次换密、不自动恢复整库，也不恢复已暴露的旧口令；保留已提交事实，进入诊断或继续验证。

### 3.3 验收判定

整体成功必须同时满足：

- 四个账号的新口令登录、`/api/auth/me`、注销均为 200，注销后原会话为 401；
- 四个旧口令均为 401；
- 改密前四个已建立会话在提交后均为 401；
- 四账号轮换后均先验证强制改密标记；管理员再通过现有 `/api/auth/password` 流程完成首次改密，验证中间口令和旧会话失效、最终口令可登录且管理员强制改密标记清除；其他三个账号仍保留首次改密要求；
- 匿名 Cookie 与非空伪造 Cookie 均不能获得授权；
- 历史业务表计数不变、数据库 `integrity_check=ok`；
- 一致性备份仍存在、SHA256 可重算，且恢复验证通过。

任何一项失败均返回非零状态，不能报告整体成功。

## 5. 回退与故障处理

- **写入前失败：** 正式库未改动；修复预检原因后重新开始，原备份保留。
- **事务内失败：** SQLite 事务回滚；核对结果状态和审计计数，禁止盲目重跑。
- **已提交但验证失败：** 不恢复旧口令、不自动整库恢复。先判断入口、代理、Cookie、API 响应类型及账号强制改密流程；必要时用同一次结果文件继续脱敏验证。
- **数据库损坏且尚未提交换密：** 可在停服、再次确认目标和获得授权后用验证过的备份恢复。
- **数据库损坏且换密已提交：** 需单独事故授权和明确的数据时间点决策，不能用旧备份把已暴露口令带回生产。

## 6. 历史清理（单独授权、单独执行）

历史重写不在工厂运行目录执行，也不是换密前置条件。演练和正式执行必须：

1. 在专用完整镜像中列举并保护全部分支、标签、PR 引用和未推送工作；
2. 宣布协作暂停，冻结推送，记录清理前引用映射；
3. 只用脱敏规则清除确认的敏感字面量，不在 Issue/PR/日志公开泄露值；
4. 验证所有可达对象、包产物、缓存与发布附件，并复跑安全扫描和关键测试；
5. 经授权后强制更新明确列出的远端引用；仓库可见性调整另行授权，不能与历史重写捆绑默认执行；
6. 隔离旧克隆和旧 worktree，禁止直接推回；协作者必须重新克隆或按书面步骤重置到新引用；
7. 保存未推送工作的补丁/分支，在净化后的新克隆中人工审阅后再移植。

## 7. frontend-v2 的独立边界

`frontend-v2` 与工厂基线无共同历史，不能合并进生产目录。当前分支虽包含依赖锁文件、Vite 配置、源码和同步包，但缺少同步包声称的构建说明。先在它自己的 worktree 补齐构建说明和隔离预览；在管理员完成全部核心业务流程与实物打印验收前，不覆盖生产静态资源或正式首页。
