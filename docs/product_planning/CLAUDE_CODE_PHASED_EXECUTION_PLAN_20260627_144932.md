# Claude Code 分阶段执行计划

> 本计划用于后续逐阶段实施。每阶段必须单独授权、备份、测试和验收，禁止一次性全部执行。

## 总体约束

1. 正式项目目录必须再次确认。
2. 每个写数据库阶段前创建可校验备份。
3. 不修改历史迁移原始层。
4. 不批量改历史订单。
5. 不删除现有功能。
6. 数据库迁移单独提交、单独演练。
7. 先写失败测试，再做最小实现。
8. 每阶段结束运行定向测试和可执行的全量测试。
9. 当前正式前端与 `tm_frontend` 不得同时无边界扩展。
10. 每阶段输出验收报告和回滚方式。

## 阶段 0：项目读取与 UI 体检（本轮已完成）

输出：

- 真实目录和技术栈
- 页面/API/数据表清单
- 纸板长宽接入情况
- 送货状态流缺口
- UI 和架构风险
- Claude Design 提示词
- 后续路线图

验收：

- 不修改代码、配置和数据库
- 结论均有代码或数据库结构依据

## 阶段 1：送货单状态流闭环（P0）

目标：

- 待发货可编辑、可删除
- 已发货可在安全条件下取消
- 取消时恢复订单已送数量
- 回单/对账后严格锁定
- 全程记录日志

影响范围：

- `app/models/delivery.py`
- `app/api/deliveries.py`
- `app/api/finance.py`
- `static/index.html`
- `static/delivery-print.html`
- Alembic 新迁移
- 送货和财务测试

设计原则：

- 送货操作状态建议为 `draft/pending/dispatched/cancelled`
- “已签收/已对账”由回单和对账关系推导，避免多表状态漂移
- 已有回单不能普通取消发货
- 已对账必须管理员按逆序反审核，不在第一小步开放

验收：

1. 待发货编辑不改变送货单号。
2. 待发货删除不改变订单已送数量。
3. 发货只累计一次。
4. 取消发货精确扣回数量。
5. 取消后订单状态正确。
6. 有回单/对账时返回明确中文错误。
7. 操作日志完整。
8. 并发重复操作被阻断。

## 阶段 2：年龄友好 UI 基础与离线资源（P0/P1）

目标：

- 建立统一 design token
- 增加标准/大字模式
- 提高按钮、输入框、表格行高
- 统一状态标签
- 将公网 CDN 依赖改为本地构建或本地静态资源

先应用页面：

- 订单管理
- 新建/编辑订单
- 送货管理
- 手机来料

影响范围：

- 优先在 `tm_frontend` 或新组件目录形成统一组件
- 旧 `static/index.html` 只做必要接入，不继续无限膨胀
- 需要明确正式前端迁移策略

验收：

- 标准/大字模式可切换并持久化
- 大字模式正文 ≥16px、按钮 ≥44px
- 手机按钮 ≥52px
- 状态不只靠颜色
- 无网络时核心页面仍能加载
- 1280×720、1440×900、手机 390px 宽均可用

## 阶段 3：手机来料两级 UI（P1）

目标：

- 默认卡片只显示纸板尺寸、数量、供应商、日期、收货按钮
- 点击展开完整详情
- 图纸/压线可点击查看
- 异常和撤回更清晰
- 移除禁止缩放设置

后端配合：

- 来料 API 补供应商、压线、供应商送货单号
- 保持权限和日志

验收：

- 一屏能看到多条待收料
- 收货按钮单手可操作
- 数量修改明确
- 未登录 401
- 异常原因必填

## 阶段 4：对账导出和公司信息（P1）

目标：

- 公司信息维护
- 送货单/对账单/标签统一读取公司信息
- 导出文件名为客户缩写 + 月份
- 对账明细补材质和状态

建议新增：

- 结构化公司设置表或现有 `system_settings` 的模块化 API
- 客户缩写字段的明确来源和唯一规则

验收：

- 修改公司信息后打印和导出同步变化
- 文件名在 Windows 下合法
- 客户缩写缺失时有稳定回退规则
- 导出按客户、月份、日期范围正确

## 阶段 5：常用箱、报料字段和 2500mm 提醒（P1）

目标：

- 确立纸板尺寸唯一来源和快照规则
- 常用箱列表直接展示纸板长宽/压线
- 增加单拼/双拼、净片/毛片、默认供应商
- 报料自动带出
- 超过 2500mm 警告

先做数据设计：

- 明确 `default_cardboard_*` 与 `report_*` 的语义
- 不直接删除旧字段
- 新字段必须副本迁移验证

验收：

- 同料号自动带出稳定
- 历史订单快照不随主数据变化
- 2500mm 只警告不禁止
- 双拼建议需要人工确认

## 阶段 6：仓库管理一期数据基础（P2）

目标：

- 片料库存
- 成品库存
- 库位
- 栈板
- 数量拆分：总量、可用、占用、损耗
- 来源追溯
- 库存流水
- 库龄提醒

建议数据表：

- `warehouse_locations`
- `warehouse_pallets`
- `inventory_lots`
- `inventory_movements`
- `inventory_reservations`
- `inventory_loss_records`
- `inventory_qr_codes`

原则：

- 片料与成品可共用批次主表，以 `inventory_type` 区分
- 每次数量变化必须通过流水
- 当前数量由事务更新并与流水校验
- 来源客户/订单/产品不可丢

验收：

- 入库、占用、出库、退回、损耗数量守恒
- 不允许负库存
- 每笔变更可追溯
- 库龄计算和筛选正确

## 阶段 7：报料库存推荐（P2）

目标：

- 系统推荐库存
- 人工确认抵扣
- 不自动扣减
- 计算最终报料数量

推荐器输入：

- 客户
- 产品/料号
- 所需材质
- 所需长宽
- 数量
- 单拼/双拼

推荐器输出：

- 候选库存
- 风险等级
- 可抵扣数量
- 浪费率
- 库位/二维码
- 库龄
- 推荐原因

验收：

- 强材质约束正确
- 尺寸不足绝不标为可用
- 克重近似仅为人工候选
- 确认前库存不变
- 确认后生成占用/流水

## 阶段 8：二维码扫码管理（P2）

目标：

- 库位、栈板、片料、成品、刀模区、印刷版区二维码
- 手机扫码查看和操作

验收：

- 二维码唯一
- 扫码显示对象类型和当前位置
- 数量操作写日志
- 取用、未使用、损耗、移库均有原因和关联订单
- 无权限不能改数量

## 阶段 9：生产单与标签打印（P2）

目标：

- 生产单
- 聚晟达标签
- 产品、片料、成品、栈板二维码标签

标签字段：

- 客户
- 产品
- 规格
- 材质
- 纸板长宽
- 压线
- 数量
- 订单/客户单号
- 生产日期
- 库位
- 二维码

验收：

- A4/标签纸打印预览正确
- 无金额字段泄露给车间
- 二维码可扫码
- 打印次数和操作人有记录

## 阶段 10：前端渐进组件化收口

目标：

- 逐页将 `static/index.html` 拆到正式组件化前端
- 旧页面保留可回退入口
- 每页迁移后单独验收

推荐顺序：

1. 送货
2. 订单
3. 报料
4. 手机来料
5. 财务
6. 主数据
7. 系统设置

禁止一次性重写全部页面。

## 每阶段通用执行模板

1. 读取交接、现有代码和相关测试。
2. 记录主库数量、SHA-256、完整性。
3. 创建备份或副本。
4. 写失败测试。
5. 实现最小闭环。
6. 在副本做结构/数据演练。
7. 运行定向测试。
8. 运行全量测试或记录阻塞。
9. 页面人工验收。
10. 生成报告、回滚命令和下一阶段建议。
