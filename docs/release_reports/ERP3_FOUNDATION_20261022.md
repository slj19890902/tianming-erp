# ERP 3.0 首批流畅性候选回执

日期：2026-10-22。用户批准按审计方案实施后，本批聚焦首页、页面切换和查询列表。业务基线为当前已核验的 v0.22.711 源码，候选分支 `codex/erp3-foundation-20261022`。这是 3.0 分阶段升级的第一批，不是完整 3.0，也未变更正式版本号。

## 状态与实际变化

开发和隔离验证通过；正式系统未发布、未停服或重启，管理员正式页面验收尚未进行。最终提交／推送身份见同目录 NAS 任务回执与候选清单。

- **读取不冻结整个工作区。** 页面读取使用独立状态；外壳和工作区采用相同的读取／写入保护合同。可用新导航替代慢读取，取消旧读取并拒绝过期响应，顺序初始化也检查页面代次。
- **保留真实业务保护。** 未保存、正在提交和结果未知仍保护；补齐片料原请求及已有补库／报料恢复状态。独立复审发现并修复“已核对成功仍锁导航”和“旧账号请求锁住新账号”两条交错路径，只有正确原请求的充分证明才能释放保护。
- **列表稳定和操作简化。** 同客户查询更新或失败时保留原表格并明确提示；切客户／账号先清旧数据。常用箱行操作改成“编辑／查看＋更多”，原有权限与动作全部保留。筛选计数与实际字段一致，末页／内容变化不反复改变容量和回源。
- **修复桌面容器。** 统一外壳按真实 iframe 宽度布局；标准模式去掉第二层横向滚动。修正大字模式在较窄桌面继承手机纵向布局导致只能显示两行的问题；独立旧页面和手机断点保持原规则。
- **后端减少重复读取。** 首页去掉最终会被覆盖的旧卡片／待办构造，补齐冻结字段避免逐行延迟查询；空客户范围提前返回。订单显示登记按本次 ID 读取，来料历史的当前工程图纸回退批量读取。衬板列表的生产任务、有效完工和半成品需求按候选 ID 分批预读，逐项实物资格、冻结预占仍调用原规则。

没有改 API 响应合同、业务资格筛选和分页顺序、数量／金额、权限／客户范围、冻结历史、幂等、写入事务、全局缓存规则或库存事实。没有新增数据库 migration。

## 对照结果

数据为 2026-10-21 历史快照的受管隔离副本；固定业务时间，四种权限上下文、五个读取场景，各重复三次。优化前后 **20 个场景的完整 JSON 哈希及权限决定相等**；同源、时点、schema、数据计数、脚本与场景顺序等十个比较门槛通过。测量阶段禁止数据库写入与外库连接，尝试数为零，数据库字节哈希不变。

| 场景 | 单次 SQL 数：前 → 后 | 确定变化 |
|---|---:|---:|
| 管理员首页 | 3494 → 3204 | 减少 8.30% |
| 车间首页 | 1816 → 1529 | 减少 15.80% |
| 空客户范围首页 | 78 → 5 | 减少 93.59% |
| 管理员／车间来料历史 | 3365 → 2861 | 减少 14.98% |
| 管理员普通订单摘要 | 325 → 325 | 登记查询范围缩小，次数不变 |
| 管理员常用箱摘要 | 4 → 4 | 本批主要改善前端展示与刷新 |

管理员首页样本中位耗时 838→791ms、来料历史 692→527ms，但每项只有三次，未清系统文件缓存，也不含 HTTP、认证、中间件、网络和页面渲染。没有 SQL 变化的场景也出现明显时间浮动，因此不把该比例当正式环境提速承诺。尚未测得正式系统的冷暖启动或 p95，不能宣布审计规划中的性能指标已全部达标。

隔离 Chrome 使用真实模板、已构建外壳和明确标注的合成资料；服务仅绑定 loopback，禁止业务写入，不导入业务应用或数据库。视觉与操作结果：

| 窗口／模式 | 验证结果 |
|---|---|
| 1296×746 标准 | 行高约203px→43px；可见10行；操作列固定；body宽1080=scrollWidth |
| 1366×768 标准 | 11行，单层表格横向滚动 |
| 1920×1080 标准 | 18行，末页6行，容量不反复跳动 |

| 1366×768／1920×1080 大字 | 分别5行／11行，页面无第二层横向滚动 |

| 失败／空结果／客户切换 | 失败保留行且可重试；空结果单独提示；切到延迟读取的另一客户即刻为0行；旧结果不回填 |
| 更多菜单 | 末行菜单向上展开、动作完整可见；ESC收起；不会撑高行 |

## 数据来源、清理与回退

原始诊断源附件受系统账号保护，受管复制准备失败后没有绕过权限。性能夹具使用此前已登记、仅调整八个PDF路径的库存读取源，再由 `run_task.py` 建立子副本。附件不在本轮范围，该夹具不代表今日正式数据质量结论。所需客户送货资料证据原字节复制至UAT根并核验哈希，没有用空证据绕过读取门禁。

本批没有删除、合并、停用或自动修复正式数据。主档缺项、歧义、停用客户关联、待上架等事项仍按原审计分别治理，不能为“干净”直接删历史事实。

受管副本因回收器无法确认进程已退出而按规则保留，原因见各runner回执；未绕过回收器手工删除。根创建的loopback视觉服务在验收结束后停止，Chrome尺寸已恢复。

本批无新schema与业务数据修正。正式发布时须先取得最新正式时点副本、受控恢复演练及签名包，复核当前正式源码是否仍与本候选父基线一致；如已有新版本，先重做差异整合。回退沿现有原生发布流程切回经过验证的前一程序包，不用旧快照覆盖正常产生的业务数据。正式发布授权前不执行停服／迁移／替换。
