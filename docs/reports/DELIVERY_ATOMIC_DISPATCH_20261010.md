## 已查明的问题

原发货接口没有员工已确认的版本和完整数量快照，旧页面可能发出他人后来修改的数量。拿货应用、随货准备和发货由页面分次提交，不能保证全部成功或全部回滚。发货在构造响应前提交，构造或传输失败时库存可能已经扣除；页面不能精确查到原请求结果。普通订单取消送货恢复待发后，迟到的旧发货请求可能再次执行。

已完成原始真实合成 HTTP 取证和实际页面方法取证，见 DELIVERY_SAVE_RECOVERY_AUDIT_20261010.md。原生重复点击已发单会被阻止、保存原键正确重放等正常保护没有算作缺陷。

## 本次实现

员工先核对服务端只读快照，再一次确认发货。后台在同一事务内核对原版本、完整单据和实际拿货，执行必要的拿货应用、随货准备、正式发货和原结果记录。任一步失败整体回滚。原请求重发优先返回原记录，取消后的旧请求不能重新扣库。正常订单仍按总量沿原资格自动跨货位扣库，员工不增加逐货位填数操作。

页面在发出前保存完整原请求，断网、超时、坏回包或刷新后仍有“查原结果”和明确的原请求操作入口；不同账号、不同弹窗和迟到回包不能串单。发货成功与后续打印、列表刷新失败分别显示。核对原结果不会自动重打。

原请求因版本变化无法继续时，可明确结束本次请求。后台同锁判断原结果：已发货则返回原完成事实；未发货则记录不可覆盖的结束凭据。页面只有收到并保存精确结束证明后才解除待核对状态，重新读取新数量供员工再次确认。未查到记录、普通错误码不等于请求已经结束。

完成证明必须包含真实扣库流水或合法直接完工分配，按明细和组件核对实际消费；缺失、损坏或数量不守恒的证明只能追溯核对，不能伪报完整成功。客户数量、物理数量及原冻结 BOM 身份保持分列。
