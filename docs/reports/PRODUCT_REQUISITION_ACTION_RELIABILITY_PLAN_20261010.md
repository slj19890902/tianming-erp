# 产品查询到报料：已复现问题及最小修复方案

2026-10-10；任务 PRODUCT-REQUISITION-ACTION-RELIABILITY-20261010。基线为已部署v607源ef952a8d，探针与正式相关源码逐字一致。此文为实施计划，尚未发布。

## 本轮先修复

1. 产品A打开订单/报料未完成，切账号或产品B后，A的回调仍能打开原订单、重置B草稿，旧查询也能覆盖B列表。动作带独立身份，每次等待后在开窗/赋值前校验当前账号、页面及原表单；组件内部旧错误不得出现在新产品。正常导航时的组件卸载与用户取消分开处理。
2. 打开动作没有有限等待，底层不返回时长期锁住按钮。开窗和查询动作设置超时，提供可重试状态并废弃迟到续步；不声称超时能撤销业务保存。
3. 外购补库旧请求在管理员/成本门禁之前返回。真实HTTP中当前boss或撤成本账号原key仍201，同内容新key403。新建和原key重放均检查当前执行、客户及管理员/成本权限，防止旧请求成为旁路。
4. 外购旧请求只比部分产品/数量，改备注或操作人仍201。使用现有request_hash在真实新单INSERT时冻结操作人和完整规范化请求；普通和并发重放均完整匹配。旧null记录不回填、不猜原请求，拒绝再次执行并说明原单核对入口；新原样重放仍用冻结采购，不受供应商停用、主档换算变化或跨日影响。
5. 已停用常用箱在工作台不能发起，但直接普通新建补库仍201。仅新建路径校验引用产品的存在、未删除及启用状态；已经成功的原请求不因以后停用而失去重放能力。

以上按根因计数，不把同根因的不同入口/坏包重复计数。新请求本来代表新业务，不把其再次建单本身记作后端幂等Bug。

## 下一闭环，不冒充本轮修复

保存后返回信息失败可以实际发生在commit之后：合成库真实HTTP500后原单仍持久，原key重放返回同ID且零新增，GET可查。当前前端未知后重新打开会丢原key/body；null或空2xx也被标成功。这需要同时完成原请求持久化、当前权限下原结果查询和完整回执验证，不能只改提示。

纸板现有request_hash不保存原body；外购旧记录更缺完整hash，不把当前可编辑单据当原始完整证明。员工申请已有申请人+key、原payload及hash，但手机跳转正确不能证明审批页面保存/恢复正确。后续分别核验真实合同，保存成功与列表刷新失败继续分开。
