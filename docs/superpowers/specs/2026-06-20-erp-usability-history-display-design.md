# ERP 正式使用体验优化与历史订单显示规范设计

更新时间：2026-06-20

## 1. 目标

本轮目标分为两部分：

1. 正式使用前人工试用准备确认
2. ERP 正式体验优化与历史订单显示规范调整

本轮明确不做以下事情：

- 不执行历史迁移
- 不直接批量修改主库历史订单号
- 不直接批量修改主库历史订单状态
- 不修改 `legacy_ruida_*`
- 不删除历史订单、历史明细或迁移台账
- 不要求 Codex 知道任何正式密码明文

## 2. 约束

### 2.1 数据约束

- 主库正式库保持：`D:\纸箱厂erp软件搭建\data\carton_erp.sqlite3`
- 当前主库基线数量不得变化：
  - `sales_orders = 15593`
  - `sales_order_items = 15658`
  - `RUIDA- = 15589`
- 历史追溯链必须保留
- 审计层可保留 `RUIDA` / `瑞达` / `中奇` 等来源字样
- 日常 ERP 页面 / API 返回不应继续暴露旧来源字样

### 2.2 实现约束

- 低风险需求优先用显示层与 API 兼容层解决
- 涉及批量改历史订单号 / 状态的需求，只能先在副本演练
- 订单管理分组优先采用前端分组，避免高风险后端聚合改造
- 图纸版本字段若主库无现成字段，不新增主库字段，只在报告说明

## 4.2 历史订单号显示规范

### 问题

当前历史导入订单号为 `RUIDA-<legacy_order_id>`，会在正式 ERP 页面 / API 中直接暴露旧来源。

### 设计

分两层处理：

#### A. 正式系统显示层

新增“显示订单号”规则，不直接修改主库 `sales_orders.order_number`：

- 对迁移历史订单：
  - 日常 UI / API 展示 `display_order_number`
  - 格式：`TMYYYYMMDD-####`
- 对新 ERP 订单：
  - `display_order_number = order_number`

#### B. 副本演练层

在副本库中演练真正把历史订单号从 `RUIDA-xxxxx` 改为 `TMYYYYMMDD-####`：

- 优先日期：`order_date`
- 其次：`created_at`
- 如都为空，使用固定归档日期并在报告说明
- 同日稳定排序并保证唯一

### 为什么先做显示层

- 可立即改善正式使用体验
- 不破坏历史追溯
- 不需要主库批量写入
- 后续若要真正改主库订单号，可先参考副本演练结果再单独授权

## 4.3 历史订单状态归档显示

### 问题

迁移历史订单不能继续混入当前待报料、待送货、待结款等待办流转。

### 设计

同样分两层：

#### A. 正式系统显示 / 查询层

为历史迁移订单建立“历史订单判断规则”，但不直接改主库状态字段：

判断依据优先：

1. 迁移台账存在
2. 或订单号匹配历史导入规则

显示逻辑：

- 列表 / 详情中增加“历史订单”标签
- 历史订单显示状态文案统一归档为：
  - 已报料
  - 已送货
  - 已结款

待办过滤逻辑：

- 历史订单不进入：
  - 待报料
  - 待送货
  - 待结款
  - 当前生产待办

#### B. 副本演练层

在副本中试演真正改动历史订单状态字段或相关状态组合，验证：

- 页面不报错
- 财务 / 对账 / 收款页面不异常
- 不再混入待办

## 4.4 常用箱 / 产品资料分页搜索优化

### 目标

- 客户列表默认每页 25
- 产品列表默认分页
- 大型选择器不一次性加载全部数据

### API 设计

统一返回：

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "page_size": 25,
  "total_pages": 0
}
```

#### 客户 API

支持：

- `keyword`：客户名称模糊搜索
- `page`
- `page_size=25`

#### 产品 API

支持：

- `customer_id`
- `keyword`
- `product_code`
- `product_name`
- `spec`
- `material`
- 分页

### 前端设计

- 增加搜索框与清空筛选
- 增加上一页 / 下一页 / 当前页 / 总页数 / 总条数
- 客户选择器改为先搜索后分页加载
- 产品选择器改为“选客户后再加载”

## 4.5 客户常用箱列表优化

### 目标字段

- 存货编码
- 产品名称
- 规格
- 材质
- 单价
- 图纸版本
- 状态
- 操作

### 设计

- 点击客户后进入该客户常用箱列表
- 表格横向并排显示
- 分页与搜索共用产品 API
- 图纸版本字段按以下优先级取值：
  1. 现有产品图纸版本关系字段
  2. 若无，则显示为空并在报告说明“主库无现成字段”

## 4.6 订单管理显示优化

### 目标

- 支持普通列表模式
- 支持按客户名称分组
- 支持按客户单号分组
- 支持按日期排序
- 同客户单号下展示子订单栏
- 历史订单显示为历史归档状态
- 页面不再显示 `RUIDA`

### 设计

优先采用前端分组：

- API 仍返回标准分页订单列表
- 前端增加视图模式切换：
  - 普通列表
  - 按客户名称分组
  - 按客户单号分组
- 分组主行显示：
  - 客户单号
  - 客户名称
  - 总金额
  - 总数量
  - 子订单数量
- 展开后显示子订单：
  - 订单号（显示规范号）
  - 日期
  - 产品
  - 数量
  - 金额
  - 状态

### 原因

- 风险低
- 不破坏现有搜索 / 分页 / 详情 API
- 如后续性能不够，再设计后端聚合接口

## 4.7 新建订单修复

### 问题

- 当前新建订单引用产品范围异常，容易混入错误客户产品
- 未选客户前不应默认出现产品
- 数量默认值与校验不够严格

### 设计

#### 前端

- 第一步必须先选客户
- 未选客户前：
  - 禁用产品选择框
  - 不显示默认纸箱名称
- 选客户后：
  - 只加载该客户的产品
- 产品选定后自动带出：
  - 存货编码
  - 产品名称
  - 规格
  - 材质
  - 单价
- 多明细每行数量默认空值
- 保存前校验：
  - 已选客户
  - 已选产品
  - 数量必填
  - 数量 > 0

#### 后端

- 创建订单接口继续做强校验：
  - 客户不能为空
  - 至少一条明细
  - 每条明细产品必须存在
  - 产品必须属于所选客户
  - 数量 > 0

## 8. 风险与回退

### 风险

- `中奇` 可能是业务真实客户名，不能盲替换
- 副本历史状态归档可能影响财务 / 对账筛选逻辑
- 前端分组可能与现有分页交互产生边界问题
- 产品分页搜索可能影响新建订单交互体验

### 回退

- 本轮正式实现优先不动主库历史数据，因此主库无批量数据回滚需求
- 副本演练失败则直接丢弃副本，不影响主库
