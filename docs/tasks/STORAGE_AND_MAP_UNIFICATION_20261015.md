## 4. 第二阶段：长期保留机制

- 正式业务只有一个权威数据根：运行库、必要事务文件、业务附件/原件、配置/密钥。恢复依赖可以多包，不强求只有一个目录；清理过程中不改变正式数据事实。
- 本地完整备份滚动保留1份有效恢复点：新备份完成且验证后才淘汰旧备份，允许生成时短暂并存；当前更新事务必需的恢复点在事务结束前保护。若恢复点依赖多个对象，按依赖整体保留，不能只按文件数截断。
- 程序保留当前版、一个有效回退点及实际需要的监督/迁移/恢复依赖；每次成功发布按引用回收旧包，失败现场仅保留最近必要一轮。监督器版本只在有兼容证据时统一，不能为少一个包冒险替换它。
- 开发保留主仓库与一个活动维护区；命令测试成功自动清大副本，失败保留最近一轮；人工验收未结束不得自动删除。构建完成即登记产物和到期条件。
- 非业务构建/缓存/测试/过期包建议软预算30GiB；低于60GiB空闲先清安全过期项。大型预演根据实测峰值另做准入，不能因预算关闭必需恢复验证；不足则暂停新大副本并报告，业务服务继续运行。
- 日志按大小轮转并设总上限，审计业务记录不按普通日志清理；小报告保留，大二进制副本按任务生命周期回收。
- 将规则落实到现有build/test/update完成钩子和维护说明，提供dry-run默认、显式apply、幂等和独立报告；不要仅写文档。无需新增常驻Codex聊天或轮询自动任务来消耗Token。
- 针对清理器测试活动引用、恢复依赖、路径逃逸、NAS未完成、失败保留、重复执行与并发状态变化；不要为每条配置写镜像测试。

7. 修复不改变库存数量/成本/单位/预占/客户归属，不伪造移库流水，不覆盖历史位置；地图发布与关联更新须原子完成，幂等重放无新增，任一步失败整体回滚，并保留审计。真实实物移库另走正常业务流程。
